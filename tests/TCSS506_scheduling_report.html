Task: Compute turnaround time and response time for three jobs of length 200 all arriving at t = 0 under FIFO. Verify with the simulator.

python scheduler.py -p FIFO -l 200,200,200 -c

Problem 4

Task: Under what conditions does SJF deliver the same schedule and average turnaround time as FIFO?

python scheduler.py -p FIFO -l 100,200,300 -c
python scheduler.py -p SJF -l 100,200,300 -c

SJF produces an identical schedule to FIFO when all jobs arrive at the same time AND are already ordered shortest-to-longest. In that degenerate case SJF has no reordering to perform, so both schedulers make exactly the same decisions. Both commands above yield Avg T = 333.3.

python scheduler.py -p FIFO -l 300,200,100 -c → Avg T = 466.7
python scheduler.py -p SJF -l 300,200,100 -c → Avg T = 333.3

With an unsorted input the two policies diverge immediately: SJF reorders to the optimal sequence while FIFO blindly runs the first job. SJF is provably optimal for average turnaround when all jobs arrive simultaneously. FIFO only matches this optimum by coincidence.

Note — non-simultaneous arrivals: if jobs arrive at different times, non-preemptive SJF can still suffer a convoy effect (a long job blocks shorter arrivals). STCF (preemptive SJF) is required to remain optimal in that scenario.

Problem 6

Task: For what time-slice value does RR produce the same schedule as FIFO?

python scheduler.py -p RR -q 200 -l 200,200,200 -c → Avg T=400 R=200
python scheduler.py -p FIFO -l 200,200,200 -c → Avg T=400 R=200
RR degenerates to FIFO when the quantum ≥ the length of the longest job. Each job runs to completion before the scheduler ever switches, so the two policies make identical decisions.

Chapter 8 — Multi-Level Feedback Queue (MLFQ)

Problem 1 — Three randomly-generated workloads

Default settings: 3 queues (Q2 = top, Q0 = bottom), quantum = 10 per queue, no I/O.

Seed 0

python mlfq.py -s 0 -c
Job List:
  Job 0: startTime=0  runTime=84  ioFreq=0
  Job 1: startTime=0  runTime=53  ioFreq=0
  Job 2: startTime=0  runTime=41  ioFreq=0

All three jobs enter Q2 simultaneously. Each exhausts its 10-tick allotment and drops to Q1, then Q0. With no I/O and runtimes much longer than one allotment, all three end up sharing Q0 in round-robin fashion. The shorter jobs (41, 53) finish before the longest (84) but only because they run out of work sooner — MLFQ cannot tell this in advance. Response time for all three is identical at t = 0 (all arrive at the same instant and share Q2 equally at first).

Seed 1

python mlfq.py -s 1 -c
Job List:
  Job 0: startTime=0  runTime=35  ioFreq=0
  Job 1: startTime=0  runTime=68  ioFreq=0

Job 0 (length 35) completes during the Q1 phase — it uses one full allotment in Q2 (ticks 0–9), one in Q1 (ticks 10–19 shared with Job 1), then its remaining 15 ticks in Q0, finishing before Job 1 reaches Q0. This demonstrates MLFQ's emergent SJF-like property: shorter jobs naturally finish in higher queues and achieve better average turnaround without the scheduler ever knowing job lengths ahead of time.

Seed 2

python mlfq.py -s 2 -c
Job List:
  Job 0: startTime= 0  runTime=24  ioFreq=0
  Job 1: startTime= 0  runTime=60  ioFreq=0
  Job 2: startTime=20  runTime=20  ioFreq=0

Job 2 arrives at t = 20 and enters Q2 fresh. At that moment Jobs 0 and 1 have already been demoted to Q1. Job 2 immediately pre-empts them and runs at Q2 priority because MLFQ always services the highest non-empty queue first. This reproduces the chapter's key insight about good response time for new and short arrivals.

Problem 2 — Reproduce chapter examples

Figure 8.2 — Single long-running job drops through queues

python mlfq.py -n 3 -q 10 -l 0:200:0 -c

The job starts at Q2, uses its 10-tick allotment, drops to Q1, uses another 10, drops to Q0, and then runs to completion (180 remaining ticks) at the bottom queue. Final finish time = 200, turnaround = 200.

Figure 8.3 — Short job arrives while long job is running

python mlfq.py -n 3 -q 10 -l 0:200:0,100:20:0 -c

By t = 100 the long job has sunk to Q0. The short job arrives at Q2 with full priority, runs its 20 ticks at Q2, finishes at t = 120 (turnaround = 20), and then the long job resumes in Q0 finishing at t = 300. The short job receives the same excellent treatment it would get under SJF even though the scheduler never knew its length.

Figure 8.4 — I/O-intensive job "games" the scheduler

python mlfq.py -n 3 -q 10 -l 0:200:0,50:200:1 -S -c

The -S flag resets a job's allotment whenever it issues I/O. The I/O-heavy job (ioFreq=1) issues I/O every tick, resetting its allotment counter each time. It permanently occupies Q2 while the CPU-bound job sinks to Q0 and is nearly starved.

Figure 8.5 — Priority boost prevents starvation

python mlfq.py -n 3 -q 10 -l 0:200:0,50:200:1 -S -B 50 -c

-B 50 forces every job back to Q2 every 50 ticks. The CPU-bound job now periodically receives time at Q2 even while the I/O job hogs the top queue between boosts, eliminating starvation.

Figure 8.6 — Better accounting stops gaming

python mlfq.py -n 3 -Q 10,10,10 -l 0:200:0,50:200:9 -c

Without -S the scheduler tracks the job's total CPU usage across I/O boundaries. The I/O job's cumulative allotment runs out and it sinks to Q1, just as a CPU-bound job would. Gaming is prevented.

Problem 3 — Configure MLFQ to behave like Round Robin

python mlfq.py -n 1 -q 10 -l 0:50:0,0:50:0,0:50:0 -c

Using a single queue (-n 1) removes all demotion logic. Every job starts in Q0 and stays there permanently, sharing the CPU with quantum = 10 in strict round-robin order. Changing -q adjusts the time slice. 

t= 0-10: Job 0  (40 remaining)
t=10-20: Job 1  (40 remaining)
t=20-30: Job 2  (40 remaining)
t=30-40: Job 0  (30 remaining)
... (repeats until all finish)

This is equivalent to running scheduler.py -p RR -q 10 -l 50,50,50. The multi-queue demotion mechanism is the only thing that makes MLFQ different from RR; removing it collapses the two policies.

Extra Credit Problem 4 — Job A gets more than its fair share

python mlfq.py -n 3 -q 10 -l 0:200:0,0:200:9 -S -c

The trick is to craft a job that issues I/O just before its allotment expires. With -S (reset on I/O) and ioFreq = 9, Job 1 issues I/O every 9 ticks — one tick before the 10-tick allotment is consumed. Each I/O resets the counter so Job 1 never uses 10 consecutive CPU ticks and never gets demoted from Q2.

JobioFreqEffective queueOutcome
Job 0 (CPU-bound)0Sinks to Q0 within 30 ticksStarved — only runs when Q2 and Q1 are empty
Job 1 (gaming)9 + -SPermanently at Q2Monopolises CPU, unfair share

Fix: track total allotment across I/O events (remove -S). Once Job 1's cumulative CPU usage reaches the allotment, it is demoted regardless of how many I/Os it issued.

Extra Credit Problem 5 — Choosing the right boost interval

# Too short — constant interruption, high overhead
python mlfq.py -n 3 -q 10 -l 0:200:0,0:200:1 -B 10 -c

# Good balance
python mlfq.py -n 3 -q 10 -l 0:200:0,0:200:1 -B 50 -c

# Too long — CPU-bound job starves between boosts
python mlfq.py -n 3 -q 10 -l 0:200:0,0:200:1 -B 300 -c

A good boost interval T satisfies:

  max_queue_allotment  <  T  <  starvation_threshold

With 3 queues and quantum = 10, a CPU-bound job can wait up to Q2-allotment + Q1-allotment = 20 ticks before reaching Q0 once boosted. Setting T ≈ 50–100 gives the CPU-bound job a fresh Q2 slot every 50–100 ticks (preventing starvation) without disrupting the I/O-heavy job so frequently that response time degrades.

Boost interval TCPU-bound jobInteractive jobVerdict
10Runs often, goodFrequently interruptedToo short — overhead too high
50Small wait, acceptableStays responsiveGood balance ✓
300Long starvation periodsRuns freelyToo long — CPU job starves

The general rule of thumb (from the chapter) is to set T to the order of seconds on real hardware — long enough to amortise boost overhead, but short enough that no job waits more than a few seconds for a CPU turn.
